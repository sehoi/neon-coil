## 1. NEON PURGE에서 가져오는 것

| 모듈 | 수정 |
|---|---|
| `core/vec.js` | 그대로 |
| `core/pool.js` | 그대로 |
| `core/grid.js` | 그대로 (공간 해시) |
| `core/rng.js` | 그대로 |
| `core/audio.js` | 효과음 이름만 교체 |
| `core/input.js` | 그대로 — 탭 큐, 터치 조이스틱, 상태 전환 시 포인터 무시까지 이미 검증됨 |
| `core/save.js` | 스키마만 교체 |
| `config.js` | 동적 논리 해상도(`export let W`), `IS_TOUCH`, `MAX_DPR`, safe-area — 그대로 |
| `render/shapes.js` | 그대로 |
| `ui/widgets.js` | 그대로 |
| `main.js` 루프 | 고정 타임스텝 + 상태 머신 골격 재사용 |

**이 재사용이 프로젝트의 절반이다.** 특히 `input.js`는 모바일에서 "버튼이 안 눌린다 / 카드가 제멋대로 선택된다"를 전부 겪고 나온 코드라, 처음부터 다시 짜면 같은 함정을 다시 밟는다.

### 반드시 지켜서 시작하는 성능 원칙 (전부 실측으로 얻은 것)

1. **`ctx.shadowBlur` 금지.** 도형 하나하나에 블러 래스터화가 붙어 비용이 폭증한다. 네온은 굵은 반투명 stroke + 얇은 밝은 stroke로 낸다. (실측 185.9ms → 8.8ms)
2. **충돌 콜백을 인라인 화살표로 만들지 않는다.** 매 프레임 수천 개의 클로저가 GC를 유발해 p99를 끌어올린다. 모듈 스코프 함수 + 모듈 변수로 컨텍스트를 넘긴다. (p99 68.5ms → 12.9ms)
3. **업데이트 루프에서 객체를 만들지 않는다.** `{x, y}` 리터럴, `map`/`filter`로 새 배열 만들기 금지.
4. **혼잡하면 스스로 줄인다.** 파티클은 풀 점유율에 따라 생성을 건너뛰고, 렌더는 화면이 붐비면 외곽 번짐 패스를 생략한다.
5. **성능은 update + draw를 함께, 분포(p90/p99)로 잰다.** 정지 화면에서 `draw`만 반복하면 실제보다 낙관적으로 나온다.
6. **최적화는 재고 나서 채택한다.** "draw call을 줄이면 빨라진다"는 직관은 Canvas 2D에서 자주 틀린다 (패턴 타일링이 3배 느렸던 전례).

## 2. 새로 설계하는 것

넷뿐이다. 나머지는 위에서 가져온다.

### 2.1 몸통 표현 — 궤적 포인트가 곧 세그먼트

가장 중요한 결정이다. 두 가지 방법이 있다.

| 방법 | 문제 |
|---|---|
| 세그먼트가 앞 세그먼트를 스프링으로 따라감 | 세그먼트 수만큼 물리 계산. 길이 400이면 프레임당 400회 × 15기 |
| **머리 궤적을 기록하고 그 위에 몸을 얹음** | 머리 하나만 움직이면 된다 ✅ |

**채택**: 머리가 `spacing`만큼 이동할 때마다 궤적에 점을 하나 추가한다. **그 점들의 배열이 곧 몸통이다.** 길이 = 점 개수.

```js
// 프레임당 이동거리가 spacing 을 넘으면 여러 점을 보간해 채운다
// (부스트 중 한 프레임에 spacing 을 넘게 이동해도 몸이 끊기지 않게)
while (movedSinceLastPoint >= spacing) {
  pushPoint(lerp(prevHead, head, t));
  movedSinceLastPoint -= spacing;
}
```

저장은 **`Float32Array` 원형 버퍼** (`[x0,y0,x1,y1,…]`). 코일당 최대 길이를 정해두고 미리 할당한다 — 프레임당 할당 0을 지키기 위해서다.

```js
const MAX_LEN = 600;
points: new Float32Array(MAX_LEN * 2)   // 코일당 4.8KB, 15기라도 72KB
head: 0        // 최신 점의 인덱스
count: 0       // 현재 길이
```

길이가 줄면(부스트 소모) `count`만 줄인다. 배열은 그대로 둔다.

### 2.2 충돌 — 세그먼트를 성기게 등록한다

머리 20개 × 세그먼트 8,000개를 전수 비교할 수는 없다. 공간 해시(`core/grid.js`)를 쓴다.

**핵심 절약**: 몸통 세그먼트를 **전부 등록하지 않는다.** 세그먼트 간격이 반지름의 0.55배이므로, **2개 걸러 하나만 등록해도 반지름으로 빈틈 없이 덮인다.**

```
등록 개수 = 총 세그먼트 / 3
15기 × 400세그먼트 / 3 ≈ 2,000개/프레임
```

머리는 자기 주변 셀만 조회한다. 그리드 셀 크기는 최대 몸 반지름의 약 2배(48px).

**자기 몸 제외**: 조회 결과에서 `seg.coil === self`면 건너뛴다. (slither.io 방식)

**머리 vs 머리**: 머리끼리는 별도로 15×15/2 ≈ 105쌍만 비교한다. 그리드에 넣을 필요가 없다.

### 2.3 NPC AI — 벡터 합산, 프레임당 상수 비용

```js
// 모듈 스코프 누산기 (할당 0)
let _aiX = 0, _aiY = 0;

function steerAI(coil, world) {
  _aiX = 0; _aiY = 0;
  addFoodAttraction(coil, world);     // 가장 가까운 먹이 방향
  addDangerAvoidance(coil, world);    // 전방 부채꼴의 남의 몸통 (가중치 압도적)
  addBoundaryAvoidance(coil, world);  // 경계까지 거리
  if (coil.ai.kind === 'hunter') addIntercept(coil, world);
  coil.targetAngle = Math.atan2(_aiY, _aiX);
}
```

- 먹이 탐색은 **그리드 조회 1회**(반경 500px). 전체 순회 금지.
- 위험 감지도 그리드 조회 1회(반경 220px).
- **AI를 매 프레임 돌리지 않는다.** 코일마다 `aiTimer`를 두고 **6프레임에 한 번**(0.1초) 갱신한다. 그 사이에는 마지막 `targetAngle`로 계속 회전한다. 15기 × 60fps = 900회/초가 150회/초로 줄고, 체감 차이는 없다.

### 2.4 렌더 — 코일 하나 = stroke 두 번

몸통을 원 400개로 그리면 draw call 8,000회다. **폴리라인 하나로 그린다.**

```js
ctx.lineCap = 'round';
ctx.lineJoin = 'round';
ctx.beginPath();
// 화면 안 구간만 moveTo/lineTo
ctx.lineWidth = r * 2 * 1.9;  ctx.globalAlpha = 0.2;  ctx.stroke();  // 외곽 번짐
ctx.lineWidth = r * 2;        ctx.globalAlpha = 1;    ctx.stroke();  // 코어
```

코일 15기 = stroke 30회. 원 8,000개와 비교가 안 된다.

**화면 밖 컬링**: 궤적을 순회하며 화면 사각형 밖 구간은 `moveTo`로 건너뛴다. 아레나 반지름 2,600px에서 화면은 1,480×720이므로 대부분의 몸통이 화면 밖이다 — 이 컬링이 없으면 컬링 있는 경우 대비 몇 배가 든다.

**LOD**: 멀리 있는(또는 화면이 붐비는) 코일은 점을 2~3개 걸러 그린다. 굵은 선이라 표가 안 난다.

## 4. 업데이트 순서

```
1. 입력 → 플레이어 targetAngle
2. AI (해당 프레임에 걸린 코일만)
3. 코일 이동 — 각도를 targetAngle 로 turnRate 만큼 회전, 전진, 궤적 점 추가
4. 그리드 재구축 (세그먼트 3개당 1개 등록)
5. 충돌 — 머리 vs 몸통, 머리 vs 머리, 경계
6. 먹이 흡인 · 흡수 · 보충
7. 파티클
8. 카메라
9. 리더보드 갱신 (0.5초마다)
```

## 5. 성능 예산 (16.6ms)

| 항목 | 예산 | 대책 |
|---|---|---|
| 코일 이동 + 궤적 | 1.5 ms | 머리만 계산. 궤적은 원형 버퍼 쓰기 |
| AI | 1.0 ms | 6프레임에 한 번, 그리드 조회 2회 |
| 그리드 + 충돌 | 3.0 ms | 세그먼트 1/3만 등록, 머리만 조회 |
| 먹이 | 1.5 ms | 그리드 조회, 화면 밖 렌더 컬링 |
| 렌더 | 7.0 ms | 코일당 stroke 2회, 화면 밖 구간 컬링, LOD |
| 여유 | 2.6 ms | |

**측정 방법은 NEON PURGE와 동일**: `update + draw`를 함께 돌리고 `getImageData`로 파이프라인을 flush한 뒤 p50/p90/p99를 본다. 정지 화면 측정은 믿지 않는다.

## 6. 구현 순서 (마일스톤)

각 단계 끝에서 **반드시 플레이해보고, 모바일 조건으로 성능을 잰다.**

| # | 마일스톤 | 검증 질문 |
|---|---|---|
| **M0** | 캔버스 + 루프 + 코일 하나가 마우스를 따라 움직인다 | 조종이 기분 좋은가? |
| **M1** | 궤적 몸통 + 먹이 + 성장 | **길어지는 감각이 재미있는가?** 여기서 재미없으면 설계를 고친다 |
| **M2** | 충돌 + 사망 + 잔해 | 죽는 게 납득되는가? 억울하지 않은가? |
| **M3** | NPC 14기 + 리스폰 | 아레나가 살아 있는가? NPC끼리도 죽는가? |
| **M4** | 부스트 + 사냥 성립 | 남을 죽이는 게 가능한가? 그게 짜릿한가? |
| **M5** | 리더보드 · 미니맵 · 경계 · 결과 화면 | 순위가 목표로 느껴지는가? |
| **M6** | 모바일 조작 · HUD 배치 · 성능 튜닝 | 폰에서 60fps로 돌아가는가? |

> **M1이 분기점이다.** 선 하나가 길어지는 것만으로 이미 재미있어야 한다.
